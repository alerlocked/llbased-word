# 麒麟工艺文件系统 — 本地部署指南

## 架构

```
麒麟笔记本 (192.168.1.101 / 192.168.13.100)     300I Duo 服务器 (192.168.13.153)
┌──────────────────────────┐                      ┌────────────────────────────────┐
│  前端  React :3000       │                      │  Docker: mindie-qwen3-30b-a3b  │
│  后端  FastAPI :8000     │ ──── 网线直连 ────→  │    Qwen3-30B-A3B :1028 (全部) │
│  MinerU  PDF解析 (CPU)   │                      │  Docker: mindie-mineru-vlm     │
│  conda env: craftdoc     │                      │    MinerU2.5-Pro  :1040 (VLM) │
└──────────────────────────┘                      └────────────────────────────────┘
```

- 全部本地，不连云端
- LLM 推理跑在 300I Duo NPU（4卡96GB，8芯片）
- PDF 解析跑在麒麟笔记本 CPU（MinerU pipeline）+ 服务器 VLM (NPU)

## 一、网络连接

两台机器通过网线直连，在不同子网，需要给麒麟机添加副 IP：

1. 网线连接麒麟笔记本和 300I Duo 服务器
2. 给麒麟机添加副 IP（已持久化到 NetworkManager）：
   ```bash
   # 查看当前配置
   nmcli con show '有线连接 1' | grep ipv4.addresses
   # 应显示: 192.168.1.101/24, 192.168.13.100/24

   # 如果没有副 IP，手动添加：
   sudo nmcli con mod '有线连接 1' +ipv4.addresses 192.168.13.100/24
   sudo nmcli con up '有线连接 1'
   ```
3. 确认能 ping 通：
   ```bash
   ping 192.168.13.153
   ```

## 二、300I Duo 服务器 — 部署 LLM 模型

### 2.1 首次：传模型文件到服务器

模型文件较大（14B 约 28G，30B 约 57G），传输需要时间：

```bash
# 从麒麟笔记本执行
scp -r ~/models/Qwen3-14B root@192.168.13.153:/home/data/
scp -r ~/models/Qwen3-30B-A3B root@192.168.13.153:/home/data/

# 部署脚本
scp ~/models/mindie-deploy/*.sh root@192.168.13.153:/root/mindie-deploy/
```

### 2.2 首次：加载 Docker 镜像

如果服务器上还没加载 MindIE 镜像：

```bash
ssh root@192.168.13.153
docker load -i ~/mindie-image.tar   # 18GB，需要几分钟
```

### 2.3 启动模型

```bash
ssh root@192.168.13.153
cd /root/mindie-deploy
chmod +x run-qwen3-30b-a3b.sh run-mineru-vlm.sh

# 启动 LLM (全部文本任务)
./run-qwen3-30b-a3b.sh      # chips 4-7, port 1028
./run-qwen3-30b-a3b.sh logs # 等待 "Daemon start success!"

# 启动 VLM (PDF 解析，可选)
./run-mineru-vlm.sh          # chips 0-1, port 1040
./run-mineru-vlm.sh logs
```

> **注意**: Qwen3-14B 和 MinerU VLM 共用 chips 0-3，不能同时运行。当前方案使用 Qwen3-30B-A3B 统一处理所有文本任务 (chips 4-7)，MinerU VLM 使用 chips 0-1。

每条命令的执行流程：

1. **创建容器** — 加载 MindIE 镜像，挂载 NPU 设备和模型目录
2. **Patch 配置** — 读取容器内默认 config.json，只覆盖需要改的字段（端口、模型路径、NPU 设备等），保留 MindIE 所有默认值
3. **启动 daemon** — source 环境变量后拉起 `mindieservice_daemon`
4. **加载权重** — 自动进行，等待 `Daemon start success!` 即表示就绪

> **关于配置方式**：脚本采用「patch 默认配置」策略，而非完全覆盖。容器内的 `/usr/local/Ascend/mindie/latest/mindie-service/conf/config.json` 是 MindIE 自带的完整配置，包含所有必填字段（`inferMode`、`tokenTimeout`、`fullTextEnabled` 等）。脚本启动后用 Python 读取该文件，只修改端口、模型路径、NPU 设备 ID 等业务字段，其余全部保持默认。这避免了因遗漏字段导致的 `type must be boolean, but is null` 等启动报错。
>
> 仓库中的 `config-2.2rc1-*.json` 文件仅供参数参考，**不会被脚本直接使用**。

### 2.4 确认模型就绪

```bash
# 看日志，等 "Daemon start success!" 出现
./run-qwen3-30b-a3b.sh logs
./run-mineru-vlm.sh logs

# 测试接口
./run-qwen3-30b-a3b.sh test
./run-mineru-vlm.sh test
```

## 三、麒麟笔记本 — 启动应用

### 3.1 一键启动（推荐）

```bash
cd ~/project/localknowledgebase-word
./start-all.sh           # 自动检查网络、模型、清理端口、启动后端
```

脚本会依次执行：
1. 检查网络连通性（副 IP 配置 + ping 模型服务器）
2. 检查模型服务（LLM + VLM）
3. 清理旧进程
4. 启动后端（保持终端运行）

也可以只检查状态：
```bash
./start-all.sh check     # 不启动，只显示各组件状态
```

### 3.1b 手动启动（备选）

```bash
cd ~/project/localknowledgebase-word
./start.sh
```

输出应显示：
```
=== Starting Craft Document System ===
Python: Python 3.10.x
Backend: mineru
```

### 3.2 启动前端

另开终端：
```bash
cd ~/project/localknowledgebase-word/frontend
npm run dev
```

### 3.3 访问系统

浏览器打开 `http://127.0.0.1:3000`

## 配置切换

### 切换 PDF 解析后端

编辑 `~/project/localknowledgebase-word/backend/.env`：

```bash
# MinerU CPU 解析（默认，推荐）
VL_SERVICE_BACKEND=mineru

# Qwen-VL NPU 解析（需在服务器启动 VLM 容器）
VL_SERVICE_BACKEND=qwen_local
```

注意：VLM 使用 chips 0-1，与 Qwen3-30B-A3B (chips 4-7) 不冲突，可同时运行。

## 常见问题

**Q: 模型启动后接口不响应？**
权重加载需要时间（14B 约 3-5 分钟，30B 约 5-8 分钟）。用 `./run-*.sh logs` 查看日志，等 "Daemon start success!" 出现。

**Q: docker load 失败？**
确认镜像文件完整：`ls -lh ~/mindie-image.tar`（应约 18GB）。磁盘空间是否够：`df -h`。

**Q: ping 不通服务器？**
检查网线、IP 配置。麒麟笔记本网络设置确认和服务器在同一网段。

**Q: MinerU 下载模型失败？**
已配置 `HF_ENDPOINT=https://hf-mirror.com` 使用国内镜像。首次解析 PDF 时会下载约 2GB 模型文件到 `~/.cache/huggingface/`。

**Q: 启动报错 `type must be boolean, but is null`？**
说明配置文件中缺少了某些 MindIE 必填的布尔字段。当前脚本采用「patch 默认配置」策略，会保留容器内默认 config.json 的所有字段，只覆盖业务参数。如果仍然出现此错误，请确认脚本是最新的（包含 `python3 -c` patch 逻辑的版本），而非旧版的 `cat > config.json` 完全覆盖方式。

**Q: 启动报错 `missing compulsory field`？**
同上。MindIE 2.2 RC1 的必填字段较多（`inferMode`、`tokenTimeout`、`e2eTimeout`、`maxLinkNum`、`dynamicLogLevelValidHours` 等），patch 策略会在默认配置基础上补充这些字段。如果使用外部 AI 工具生成的配置，注意不要加 MindIE 不认识的字段（如 `precisionMode`、`quantMode`、`cacheSizeGB` 等），也不要把 `ScheduleConfig` 放在 `BackendConfig` 外面。
